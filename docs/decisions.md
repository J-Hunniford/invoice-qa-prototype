# What changed, and why

The spec was drafted and validated first. The prototype was built to that spec, and building it changed the spec eleven times.

Reviewing a document catches requirements that can't be tested. Building the feature catches requirements that are wrong: a criterion that reads cleanly on the page but tells a customer something untrue, or leaves an invoice unpaid that could have been settled in a click.

Those are requirements defects, not coding defects. Catching one at this stage costs hours. Catching it once engineering has built to the spec costs weeks.

Prototyping doesn't finish discovery. The spec still has open questions that need customer research, architecture and legal.

Versions that carried only copy edits are omitted from the table below. The spec itself is [`invoice_qa_feature_spec.md`](invoice_qa_feature_spec.md).

| Version | Change |
|---|---|
| v0.3 | **Building the prototype exposed a gap in the spec.** The clarify-ambiguity criterion assumed a state in which no single invoice was in view, but nothing defined how a customer reached that state or whether asking without one was allowed, so its path was potentially unreachable. Added **AC7** (question context is explicit and visible) and **AC8** (changing context clears a displayed response). |
| v0.4 | Added **AC9**: automated answers are disclosed as such, at the panel and again on every response, because panel-level disclosure alone does not survive a response being screenshotted or forwarded. The reasoning is as much commercial as ethical. An automated answer that reads as the merchant's own statement turns a wrong answer into the merchant's liability. |
| v0.6 | Added **AC10**: an unanswered question can be routed to the merchant. The withdrawn v0.5 draft inferred how a merchant's support is structured; this specifies only what the feature does, and offers an action that forwards the question with its invoice context rather than telling the customer to go and make contact themselves. |
| v0.7 | **Two measurement faults in Success Metrics.** The support-load metric assumed merchants run a ticketing system. SMBs generally do not: invoice questions reach the owner or a single admin by phone and email, outside anything the platform instruments. Replaced with question deflection rate, which is observable, plus merchant-reported load by survey, and an explicit note that deflection is a proxy and the self-report is the only read on the real outcome. |
| v0.8 | **A validation pass over the hand-edited versions found five internal inconsistencies, three of which would have changed what engineering built.** The worst: the pick-list's disambiguation window was 90 days while retrieval spanned 12 months, so an ambiguous question about an older invoice matched no criterion at all and was answerable only by guessing, which is the outcome that criterion existed to prevent. |
| v0.9 | **The handoff rebuilt around consent.** Using the running prototype showed AC4 telling a customer their dispute had been flagged for the merchant's support team when nothing had been sent anywhere. Routing now requires the customer to choose it, the question they put to the assistant is never forwarded, and **AC12** was added to state that choosing neither route transmits nothing. |
| v0.10 | **Retrieval bounded by entitlement, not only by date.** Opening an invoice in the prototype surfaced a merchant's internal note, written about the customer, on the customer's own screen. Merchant annotations are now stripped where records are retrieved, so they reach neither the screen nor the model. |
| v0.11 | **Payment made the primary route, and Goals reordered around it.** A payer asking whether they would incur a late fee was answered correctly and then offered only a conversation with the merchant, on an invoice they could have settled in one click. The feature exists to shorten time to payment, so **AC13** now offers paying ahead of any route to a person. |
| v0.12 | **Scoped to a single invoice, and reachable only from it.** The feature had its own panel with an invoice picker, so a customer could ask about one invoice while looking at another. Moving it inside the open invoice removed that class of error rather than handling it, and withdrew the clarify criterion, its pick-list, and the "which invoice is this about?" step in the handoff along with it. |
| v0.13 | **The notification route withdrawn; one way to reach a person.** AC10 offered two, writing a message or sending a bare note that a query existed. The second told the merchant something had happened without saying what, so their only move was to make contact and ask, which is the round trip this feature exists to remove. |
| v0.14 | **Payment offered on dispute-shaped questions, below the route to a person.** AC13 had suppressed payment wherever a question sounded like a complaint, which is not the same as an invoice being contested. Someone annoyed about a late delivery usually still owes the money, and removing the payment route guaranteed the invoice sat unpaid while they wrote and waited. Suppression now keys on the invoice, not on how the question was classified. |
| v0.16 | **The withdrawn clarify criterion removed from the document, and AC2b renumbered to AC3.** It had been kept as a heading recording its own absence, with nothing to build or test. Removing it freed the number, and AC2b was only ever lettered because it arrived after the numbering was set. AC4 to AC14 are unchanged. |
| v0.17 | **The record keeps every message, not just the last one.** AC14 said "a record of what was sent remains available", which the prototype implemented as one record per invoice. Sending a follow-up therefore erased the message before it. That defeats the reason the record exists: the case it was written for is a customer who wrote in anger and wants to check later what actually left, and a polite second message would have deleted the angry first one. The criterion now says every message. |
| v0.18 | **Behavioural history scoped out of this feature.** The platform holds payment, dispute and query history per payer; none of it varies what a payer is told here. Varying outreach by behaviour is a collections concern for the outbound channels, so this is a scope line rather than a position on it. |
